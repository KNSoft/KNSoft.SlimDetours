# Implement ARM64EC Compatibility

## ARM64EC compatibility issues with other libraries

[Windows on Arm (WoA)](https://learn.microsoft.com/en-us/windows/arm/overview) enables interoperability between x64 and ARM64 instructions through the [ARM64EC ABI](https://learn.microsoft.com/en-us/windows/arm/arm64ec-abi), allowing x64 and ARM64EC processes to load both types of binary modules: instructions in x64 modules run under emulation, while ARM64EC modules run ARM64 instructions natively.

ARM64EC provides [FFS](https://learn.microsoft.com/en-us/windows/arm/arm64ec-abi#fast-forward-sequences) (Fast-Forward Sequences, x64 functions) for architecture-dependent inline-hooking scenarios. However, when the target address points directly to ARM64EC code without passing through an [FFS](https://learn.microsoft.com/en-us/windows/arm/arm64ec-abi#fast-forward-sequences), such as a COM interface vtable entry exposed by some system ARM64EC modules, common hooking libraries still treat the target instructions as x64 in both x64 and ARM64EC builds. They write an x64 jump and trigger a `STATUS_ILLEGAL_INSTRUCTION` exception when it executes; see Detours issues [#292](https://github.com/microsoft/Detours/issues/292) and [#355](https://github.com/microsoft/Detours/issues/355).

## SlimDetours implementation

For the complete implementation, see [KNSoft.SlimDetours #30](https://github.com/KNSoft/KNSoft.SlimDetours/pull/30); its key points are summarized below.

### Detect the target code type

[`RtlIsEcCode`](https://learn.microsoft.com/en-us/windows/win32/api/winnt/nf-winnt-rtliseccode) detects whether target code is ARM64 emulation-compatible:

- Although the official documentation lists `kernel32.lib` as its import library, it is actually implemented by the export of the same name in `ntdll.dll`.
- Although its declaration in the Windows SDK is guarded by `#if defined(_M_ARM64EC)`, binaries built for x64 can still call it; `ntdll.dll` on both ARM64 and x64 Windows 11 exports this function.
- Internally, it reads `PEB::EcCodeBitMap`; see [KNSoft.NDK: [NT:RTL] Implement `_Inline_RtlIsEcCode`](https://github.com/KNSoft/KNSoft.NDK/commit/d31d310347040e5f4e69a74e48b71f4be332c33b) for a reference implementation.

### Process both instruction sets

To let ARM64EC builds process both x64 and ARM64 code:

- Instruction-processing functions match the compilation target platform by default; functions that process ARM64 instructions use the `_arm64` suffix, such as `detour_skip_jmp_arm64`, `detour_copy_instruction_arm64`, and `detour_gen_jmp_immediate_arm64`, and are also compiled in ARM64EC builds.
- The added `detour_skip_jmp_arm64ec` selects `detour_skip_jmp` or `detour_skip_jmp_arm64` by target code type.
- `SlimDetoursCopyInstruction` and `SlimDetoursCodeFromPointer` detect the code type themselves outside transactions.

### Trampoline compatibility

In ARM64EC builds, trampolines must support both x64 and ARM64EC architectures:

- ARM64EC trampolines are allocated by `NtAllocateVirtualMemoryEx` with the `MEM_EXTENDED_PARAMETER_EC_CODE` parameter, while x64 trampolines continue to use ordinary executable memory.
- Target patches and trampoline jump-back code are generated by code type: ARM64EC targets use ARM64 indirect jumps, while x64 targets continue to use x64 jump sequences.

### Why can't x64 builds generate a generic bridge for ARM64EC target functions?

When an x64 hook module hooks an ARM64EC target, the call chain requires two ABI transitions:

- The ARM64EC target jumps to the x64 detour, requiring an Exit Thunk.
- The x64 detour calls the original function through the trampoline, requiring an Entry Thunk.

The parameter and return-value conversions performed by [Entry/Exit Thunks](https://learn.microsoft.com/en-us/windows/arm/arm64ec-abi#entry-and-exit-thunks) depend on the function signature; the x64 compiler does not generate ARM64EC Thunks, and we cannot generate them from function addresses alone.

An ARM64EC hook module hooking an x64 target likewise requires two ABI transitions, but the function signatures are available in the hook code: the compiler generates an Entry Thunk from the ARM64EC detour's signature and an Exit Thunk for the call to the x64 trampoline through the typed original function pointer. When hooking an ARM64EC target, the target, detour, and trampoline all use the ARM64EC ABI, so no conversion is required.

Therefore, x64 builds check both the original and resolved target addresses before hooking and return `HRESULT_FROM_NT(STATUS_NOT_SUPPORTED)` upon finding ARM64EC code. Such targets should be hooked with an ARM64EC hook module. If Windows makes these target entry points refer to [FFS functions](https://learn.microsoft.com/en-us/windows/arm/arm64ec-abi#fast-forward-sequences) in the future, x64 hook modules would then be better able to support such targets.

## Compatibility validation

All combinations below were tested on a native ARM64 machine using the [COMHook](../../../Source/Demo/COMHook.c) test logic to hook `IStream::Read`. The EXE determines the process architecture; the hook module architecture is listed separately.

| Process | Hook module | Target code | Microsoft Detours | SlimDetours |
| --- | --- | --- | --- | --- |
| x64 | x64 | ARM64EC | **Crash** (`STATUS_ILLEGAL_INSTRUCTION`) | **Error** (`STATUS_NOT_SUPPORTED`) |
| x64 | ARM64EC | ARM64EC | **Crash** (`STATUS_ILLEGAL_INSTRUCTION`) | Pass |
| ARM64EC | x64 | ARM64EC | **Crash** (`STATUS_ILLEGAL_INSTRUCTION`) | **Error** (`STATUS_NOT_SUPPORTED`) |
| ARM64EC | ARM64EC | ARM64EC | **Crash** (`STATUS_ILLEGAL_INSTRUCTION`) | Pass |
